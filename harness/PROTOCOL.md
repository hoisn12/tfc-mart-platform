# Agent 협업·검증·복구 절차

## 실행과 인계

1. 메인은 사용자 허용 Phase, 이전 gate, 현재 파일 해시, 원본/기존 설계를 읽는다. 이전 완료 기록이 있어도 독립 증거가 없으면 승인으로 승격하지 않는다.
2. TASKS.md에 task ID·정확한 파일 목록·소유자·상태·계약 버전/해시·보고서 경로를 쓴다. 광범위 디렉터리만 배정하지 않는다. 중첩 파일, rename 양쪽 경로, 생성 파일도 잠금 대상이다.
3. 템플릿 task.md로 전달한다. Agent는 수신 즉시 역할·입력·범위·잠금·완료 조건을 확인하고 범위 밖 변경 필요 시 요청만 반환한다.
4. architect가 다음 구현 범위의 OpenAPI 및 behavior 문서와 필요한 ADR을 작성한다. backend/frontend는 순차 또는 읽기 병렬 검토만 한다. reliability가 실패/재시도/복구 계약을 읽기 검토하고 새 reviewer가 독립 검증한다.
5. 메인이 계약 파일별 SHA-256과 검토 보고서를 기록해 동결한다. 계약 초안, 200 응답 예시, 구두 동의만으로 구현을 열지 않는다. **Backend와 Frontend 병렬 쓰기는 계약 동결 후만 허용한다.**
6. API 변경/불일치 발견 시 두 구현을 멈추고 잠금 회수·최종 해시를 확인한다. architect 변경·ADR(중요 변경)·재검토·재동결 후 새 task로 재개한다.
7. 작업자는 report.md로 실행 명령/종료 코드/로그·미완료를 제출한다. 메인은 쓰기 종료와 잠금 해제를 확인한다. 작성자 테스트 통과만으로 Phase를 닫지 않는다.
8. 메인은 산출물 파일별 SHA-256과 해당 시점 보관본을 만들고 새 reviewer 검증 task를 연다. 보관 경로는 reports/phase-N/attempt-A/snapshot/원래경로다. reviewer는 수정 없이 재현·검증하며 증거가 없으면 BLOCKED다. 독립 검증 중 대상 파일을 변경하면 판정은 무효다. 재시도는 A를 증가시키고 이전 gate/실패 보고서/보관본을 보존한다.
9. 실패는 원소유자에게 돌리고 새 시도 보고서로 수정·재검증한다. reviewer가 수정과 승인을 겸하지 않는다. 메인은 최종 gate.json의 evidence 해시를 대조하고 check_gate.py를 실행한 뒤에만 PASS를 기록한다.

Agent는 메인에게만 파일 수정 요청·범위 확대를 전달한다. 메인이 다른 소유자에게 라우팅한다. 메인도 Agent가 잠근 파일을 동시에 고치지 않는다. reports/state/PROGRESS에는 비밀값과 실제 수신자 정보를 넣지 않는다.

## 상태와 품질 게이트

task 상태: PLANNED → RUNNING → VERIFYING → DONE. 실패는 FAILED, 필수 정보/환경 부족은 BLOCKED. DONE은 task 인수 조건 충족이며 Phase PASS와 별개다.

Phase 상태: NOT_STARTED → IN_PROGRESS → VERIFYING → PASS. 실패는 FAIL, 필수 자료 부족은 BLOCKED. 재시도는 원인/변경/새 보고서/새 스냅샷을 기록하고 IN_PROGRESS로 돌아간다. 종료된 Phase를 다시 수정하면 해당 gate와 후속 의존 gate를 무효로 표시한다. 다음 Phase의 승인된 범위에서 문서/코드가 진화하는 경우 과거 보관본을 유지하고 현재 Phase의 새 계약·회귀 증거·스냅샷으로 검증한다. 과거 gate는 당시 보관본을, 현재 gate는 보관본과 현재 작업 파일 양쪽을 검사한다. 이전 승인을 소급해 꾸미거나 보관본을 수정하지 않는다.

필수 증거 범주: requirements, contract, tests, recovery, rollback, operations, independent_review. Phase 0에서는 tests/recovery/rollback/operations가 실행 성과가 아닌 **검증 가능한 계획의 리뷰**를 의미한다. Phase 1 이후는 관련 테스트 실제 실행 결과가 필요하다. 해당 기능이 미래 Phase 범위이면 그 사실과 현 Phase의 경계/회귀 검증을 적고 필수 현 Phase 검사 자체를 생략하지 않는다.

gate JSON은 프로젝트 자체 기록 형식이며 Codex 설정 키가 아니다. check_gate.py는 누락·미실행·해시 변경·이전 gate 실패를 거부한다. 명령 결과의 진실성/검토자 신원은 스크립트만으로 보장되지 않으므로 세션 기록·원문·로그를 메인이 대조한다. 스크립트를 호출하지 않고 다음 Phase를 실행하는 것은 공통 규칙 위반이다.

## 장애·중단·컨텍스트 재개

- Agent 종료/시간 초과: 해당 task를 BLOCKED로 기록한다. 종료를 확인하기 전 잠금을 풀거나 후임을 배정하지 않는다. 작성 중 파일을 완료물로 간주하지 않는다.
- 재개: 원장→활성 스레드→파일 해시/차이→마지막 gate→계약 순서로 대사한다. 중단 시점·변경·미완료·재현 명령을 보고서에 남긴다. 오래된 잠금을 시간만 보고 자동 해제하지 않는다.
- 충돌: 두 작업을 중단하고 파일/계약별 변경을 보존한다. 메인이 소유자 하나를 배정해 통합하고 관련 테스트와 독립 리뷰를 다시 실행한다.
- 검증 실패: 다음 Phase 배정 금지. 환경 문제도 NOT_RUN/BLOCKED이며 PASS가 아니다. 보안/복원/실발송 차단 실패는 즉시 해당 작업 정지.
- 롤백: Git 저장소가 준비되면 시작 커밋/작업 diff를 남기고 영향 파일만 되돌리는 변경안을 검증한다. 현재 Git이 없으므로 구축 시 원본 해시/내용을 보존하며 Git rollback을 실행했다고 주장하지 않는다. git reset --hard/clean, 데이터 삭제, 타 작업 덮어쓰기 금지.
- DB 복구: expand/contract 호환 migration + 앱 이전 버전 원복, 비운영 사본 복원/대사. 새 쓰기를 잃는 단순 스냅샷 복귀 금지. SMS 외부 부수효과는 되돌릴 수 없으므로 UNKNOWN/발송대장/큐를 보존해 중복 방지.
- 운영 전환은 승인 문서·역할·관찰 임계값·중단·원복 계획을 준비해 운영 담당자에게 인계한다. Agent가 Production을 직접 변경하지 않는다.
